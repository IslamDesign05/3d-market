# 3D-Market — резервное копирование и восстановление

## Что резервируется автоматически

Workflow `.github/workflows/backup.yml` запускается ежедневно в 03:17 UTC и вручную через GitHub Actions → 3D-Market backups → Run workflow.

1. **Исходный код и история Git:** полный Git bundle со всеми refs и отдельный архив текущего исходного кода.
2. **Supabase PostgreSQL:** зашифрованный дамп базы данных, если настроены оба GitHub Actions secrets:
   - `SUPABASE_DB_URL`
   - `BACKUP_ENCRYPTION_PASSPHRASE`

Артефакты GitHub Actions хранятся 90 дней. Это оперативная копия, а не бессрочный архив. Ветка `stable` создана как отдельная точка возврата исходного кода. Обновлять её следует только после проверки сайта.

## Первичная настройка резервной копии Supabase

1. Откройте GitHub → репозиторий `IslamDesign05/3d-market`.
2. Перейдите в Settings → Secrets and variables → Actions.
3. Нажмите New repository secret.
4. Создайте `SUPABASE_DB_URL`. Значение возьмите в Supabase → Project Settings → Database → Connection string. Используйте URI для подключения PostgreSQL; если прямое подключение недоступно из GitHub Actions, выберите Session pooler. Не публикуйте строку подключения.
5. Создайте `BACKUP_ENCRYPTION_PASSPHRASE`: длинную уникальную парольную фразу (не менее 32 случайных символов). Сохраните её в менеджере паролей и отдельно от GitHub. Без неё зашифрованный дамп восстановить нельзя.
6. Откройте Actions → 3D-Market backups → Run workflow. После выполнения проверьте, что появились оба артефакта: `3d-market-repository-...` и `3d-market-supabase-db-...`.

**Важно:** пока оба секрета не добавлены, автоматически сохраняется только код сайта. Workflow явно покажет, что дамп базы пропущен.

## Как скачать резервную копию сайта

1. GitHub → Actions → выберите успешный запуск `3D-Market backups`.
2. Внизу страницы найдите Artifacts.
3. Скачайте `3d-market-repository-...`.
4. Распакуйте ZIP. Внутри:
   - `3d-market-all-refs.bundle` — история Git и ветки;
   - `3d-market-source.tar.gz` — исходный код на момент копирования;
   - `SHA256SUMS` — контрольные суммы.

Проверить bundle локально можно командой:
```bash
git bundle verify 3d-market-all-refs.bundle
```

Восстановить историю в новую папку:
```bash
git clone 3d-market-all-refs.bundle 3d-market-recovered
```

## Как вернуть рабочую версию сайта

### Вариант A — откатить неудачные изменения через GitHub

1. Откройте репозиторий → Commits.
2. Найдите последний коммит, когда сайт точно работал.
3. Откройте его и создайте новую ветку от этого коммита либо используйте Revert для ошибочного коммита.
4. Создайте Pull Request в `main`, проверьте изменения и только затем объедините его.
5. Дождитесь успешной публикации GitHub Pages.

Не удаляйте и не переписывайте историю `main` принудительным push.

### Вариант B — восстановить из Git bundle

1. Скачайте артефакт резервной копии и распакуйте его.
2. Выполните `git bundle verify 3d-market-all-refs.bundle`.
3. Выполните `git clone 3d-market-all-refs.bundle 3d-market-recovered`.
4. Проверьте сайт локально и перенесите нужный коммит в GitHub через отдельную ветку и Pull Request.

## Как расшифровать дамп Supabase

1. Скачайте артефакт `3d-market-supabase-db-...` из успешного запуска.
2. Распакуйте ZIP и проверьте файл командой:
   ```bash
   sha256sum -c SHA256SUMS
   ```
3. Установите PostgreSQL client и GnuPG.
4. Расшифруйте файл, используя сохранённую парольную фразу:
   ```bash
   gpg --output supabase-database.dump --decrypt supabase-database.dump.gpg
   ```
   GnuPG запросит парольную фразу.
5. Проверьте дамп:
   ```bash
   pg_restore --list supabase-database.dump
   ```

**Не запускайте восстановление всей базы в рабочем Supabase вслепую.** В Supabase есть управляемые схемы и служебные объекты; восстановление следует планировать с учётом версии PostgreSQL, схем и политик RLS. Сначала безопаснее восстановить дамп в отдельный тестовый проект Supabase и проверить таблицы, данные, функции и политики. Не выполняйте `pg_restore --clean` на production без отдельного плана и проверенной копии.

## Что эта система не заменяет

- GitHub Actions artifacts удаляются по истечении 90 дней.
- Ветка `stable` находится в том же GitHub-репозитории и не защищает от потери всего GitHub-аккаунта или репозитория.
- Парольная фраза шифрования должна храниться отдельно. Потеря фразы означает потерю доступа к зашифрованным дампам.
- Восстановление кода не восстанавливает автоматически настройки Supabase Auth, URL Configuration, SMTP, GitHub Secrets или DNS.
- Секреты и ключи Supabase нельзя добавлять в репозиторий. Используйте только GitHub Secrets.
- Для дополнительной защиты скачивайте важные резервные копии на отдельный компьютер или внешний диск.

## Регламент

- Ежедневно: автоматический backup через GitHub Actions.
- После каждого крупного изменения: вручную запустить workflow и проверить артефакты.
- Перед изменениями схемы Supabase: создать и проверить отдельную резервную копию базы.
- После проверки нового релиза: обновить ветку `stable` только на заведомо рабочий коммит.
- Раз в месяц: проверить, что артефакты скачиваются, контрольные суммы проходят, а дамп открывается через `pg_restore --list`.
